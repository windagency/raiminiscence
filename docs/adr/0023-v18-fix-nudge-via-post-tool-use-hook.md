# v18 detects a Watched Command's failure→fix transition via `PostToolUse`/`PostToolUseFailure` hooks, and nudges the agent to `remember` it rather than writing the Memory itself

[Back to CONTEXT.md](../../CONTEXT.md) • [Back to docs/adr/README.md](README.md) • [Back to flows.md](../architecture/flows.md) • [Back to hld.md](../architecture/hld.md) • [Back to lld.md](../architecture/lld.md) • [Back to user-guide.md](../user-guide.md) • [Back to packages/raiminiscence-hooks/README.md](../../packages/raiminiscence-hooks/README.md)

Today, capturing a build/typecheck/test failure and its eventual fix as a Memory depends entirely on the agent proactively deciding to call `remember` — there is no mechanism tying "this command just failed" to "this command just succeeded" at all, so the same mistake can go uncaptured indefinitely if the agent doesn't happen to think of it. This was flagged as a gap in rAIminiscence's own design (the project observes agent-authored content passively; it never observes tool output itself) rather than a bug, and scoped into its own design session.

## Decision

**Hook-nudged, not hook-authored.** The new hook detects the failure→fix transition and injects a suggestion for the agent to call `remember` itself; it never calls `remember` on the agent's behalf. Rejected alternative: have the hook write the Memory directly, fully removing the agent from the loop. Rejected because every hook in this project is a plain deterministic script with no LLM access (confirmed against `raiminiscence-hooks`'s own dependencies) — a hook-authored Memory could only ever contain a raw stderr dump, never a synthesized root cause or solution, which is the entire point of capturing this at all. This mirrors Checkpoint's existing precedent (`Stop`-hook nudge, ADR-0020): the server has no LLM of its own; content is always agent-authored via `remember`.

**Fires only at the fix, not at the failure.** The hook stays silent when a Watched Command fails, and nudges only once that same Watched Command later succeeds. Rejected alternatives: nudging at failure time (the agent hasn't found the root cause yet, so the resulting Memory would be premature or simply ignored), and nudging at both points (redundant — a failure-time nudge adds no information the fix-time nudge doesn't already carry, since the fix-time nudge includes the captured failure details too).

**New hook-internal state ("Open Failure"), deliberately not folded into Checkpoint.** Detecting the transition needs a per-session record of each Watched Command's last failing invocation (command string + truncated stderr). Checkpoint (v13) already persists session-scoped state refreshed via a hook, which looks mechanically similar. Rejected reusing it: Checkpoint is agent-authored content, an ordinary Recall candidate, and a Memory Kind subject to decay/Pruning; Open Failure is hook-only control-flow bookkeeping that must never be recalled as a Memory. Giving Checkpoint a second, unrelated job would make its own definition harder to reason about for no benefit — a separate state file (same on-disk pattern as `checkpoint-nudge.ts`'s per-session JSON file, keyed by Watched Command pattern instead of a single record) keeps the two concerns apart.

**Session-scoped only, no cross-session carry.** A failure left open past a session boundary is simply forgotten — the next session starts with no Open Failure state. Rejected persisting it across sessions: that needs its own expiry/cleanup story (an Open Failure nobody ever revisits would otherwise accumulate indefinitely), and a build left broken across a whole session boundary is unusual enough not to design for up front.

**Opt-in via a configured pattern list ("Watched Command"), not automatic detection.** A new `watchedCommands` field on `.raiminiscence.config.json` (substring/regex patterns matched against the full command string, empty/absent by default) gates which commands this applies to. Rejected alternatives: treating *any* nonzero-exit shell command as a failure (extremely noisy — a `grep` with no match, `test -f`, and `git diff --quiet` all "fail" by design without being bugs), and guessing at common build/test tool invocations across languages with a fixed heuristic (guesses wrong on unusual setups, and this project already has a config-surface precedent — `embeddingProvider`, `sharedMemory`, `maxHops` — for exactly this kind of per-project variation).

**Claude Code only for v1, wired to two events rather than one.** Confirmed directly against Claude Code's own hooks documentation (superseding this ADR's original draft, which assumed a single `PostToolUse` event carrying an `exit_code` field for both outcomes): `PostToolUse` fires only when a tool call *succeeds*, and a failing Bash command instead fires the separate `PostToolUseFailure` event. Neither carries a literal `exit_code` field the way the original draft assumed — `PostToolUse`'s Bash `tool_response` is `{stdout, stderr, interrupted, isImage}` (success is implied by the event firing at all), while `PostToolUseFailure`'s payload is a single `error` string whose first line is `Exit code N`, followed by the command's stdout and stderr already interleaved into one block (no separate `stderr` field). `shim.ts` therefore dispatches both events to the same Fix Nudge engine, translating each event's distinct shape into the engine's client-agnostic `{command, exitCode, stderr}` outcome first. Both events can inject `additionalContext` back to the agent immediately. Cursor and Codex CLI's nearest equivalents are unverified against primary documentation as of this writing (Cursor's `afterShellExecution` is reported as observe-only with no exit code; a separate injecting `postToolUse` hook is reported but unconfirmed; Codex CLI's equivalent is similarly unconfirmed). This is the same shape as [ADR-0015](0015-v10-per-turn-auto-recall-excludes-cursor.md)'s Cursor exclusion for Per-Turn Auto-Recall and [ADR-0020](0020-v13-checkpoint-via-stop-hook.md)'s Codex CLI exclusion for Checkpoint — a genuine, currently-unverified per-client capability gap, not a workaround to design around. Other clients pick this up once/if their equivalents are confirmed.

**The nudge carries the raw failure details, truncated to the last 40 lines of stderr.** Rejected a generic pointer ("something you fixed might be worth remembering") with no failure content attached: the entire motivation here is not relying on the agent to still have the failure in its own context, and a bare pointer reintroduces exactly that reliance. Rejected truncating from the top of the output instead of the tail: compiler and test-runner output puts its actionable summary at the end, with setup/progress noise earlier.

**An aborted `PostToolUseFailure` (`is_interrupt: true`) is skipped entirely — no Open Failure recorded, no nudge.** Claude Code sets `is_interrupt` when the failure reached it as a Ctrl-C/abort rather than a reported command failure, which isn't a genuine failure worth tracking or nudging on.

This is a design decision only; implementation (the `packages/raiminiscence-hooks` module, the `watchedCommands` config resolution, `shim.ts`'s `PostToolUse`/`PostToolUseFailure` dispatch, and tests) is left to the accompanying v18 spec.
