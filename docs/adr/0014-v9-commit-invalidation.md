# v9 Commit Invalidation stales Memories via commit-message text, not Related Files

[Back to CONTEXT.md](../../CONTEXT.md) • [Back to docs/adr/README.md](README.md) • [Back to hld.md](../architecture/hld.md) • [Back to lld.md](../architecture/lld.md)

Invalidation only ever catches drift for a Memory whose author populated `relatedFiles` up front. Anything else — most commonly a Decision Memory an agent never anchored, or wrote before it was clear which files would matter — has no path to `stale` at all except Promotion Audit's unrelated triggers, which only apply to a Semantic Memory's `promotedFrom` contributors in the first place. A Decision Memory recording "we use webpack for bundling," never given `relatedFiles: ["webpack.config.js"]`, keeps presenting itself as current fact through every future Recall/Overview even after the project migrates to a different bundler entirely — nothing in Consolidation ever catches it.

We chose Commit Invalidation, a new Consolidation-time step, deliberately kept separate from Invalidation rather than folded into it: Invalidation stays anchored to Related Files/git-diff evidence specifically, Commit Invalidation stays anchored to commit-message text specifically, and a Memory is only ever a candidate for the latter when it has no `relatedFiles` set at all — the exact complement of Invalidation's own eligibility, so the two never compete to stale the same Memory. It reads a commit's subject line only (never its diff or body), extracts a target phrase when that subject matches one of a small set of migration/breaking-change shapes (`migrate X to Y`, `replace X with Y`, `deprecate X`, `remove/drop X`, and near-synonyms) — the target is always the outgoing thing being moved away from, not the thing replacing it — and flags every eligible Memory whose full body contains that phrase as a case-insensitive, word-boundary-matched substring. We chose plain substring matching over a fuzzy token-overlap scorer deliberately: token-overlap needs a tunable threshold and a second heuristic layer to justify, and nothing about this project's own Memory content has demonstrated plain substring matching is insufficient — that added complexity would be speculative, not evidence-driven. The same reasoning governs the commit range: rather than a rolling day-based window, Commit Invalidation scans the same unbounded git history Invalidation already scans, filtered per-Memory against that Memory's own `createdAt`, since Invalidation already proved that scan cheap enough in practice and a rolling window would introduce a new configuration surface this project has avoided since v5. A minimum-length/stopword guardrail on the extracted target exists specifically because plain substring matching, unlike token-overlap, makes a short, common extracted word dangerous on its own — rejecting trivial targets before the substring check runs is load-bearing here in a way it wouldn't be for a fuzzier matcher.

This is the first ADR to document a rationale for git-message-driven invalidation at all, including for the mechanism it complements — Invalidation's own original file-touch design shipped without one. Commit Invalidation is automatic and unconditional, no new tool and no config flag, matching v5 through v8's precedent that this project's evidence-driven `stale` gates never need an opt-in; a `stale` transition is non-destructive and has no reversal path, the same immutability principle Invalidation, Promotion Audit, and Forget already follow, so a false-positive substring match costs a maintainer an unnecessary re-remember rather than lost data. It lives in its own module and reports its own `consolidate` result count, kept separate from `memoriesInvalidated` — never combined, matching the standing discipline against conflating what separate mechanisms count, first established at v7.

Sequencing resolves a tension between this feature's own acceptance criteria and its first instinct to sit at "the same pipeline position as Invalidation:" existing Invalidation runs after Pruning's physical deletion, so a Memory eligible for both Pruning and Invalidation in the same pass is simply gone — deleted — before Invalidation ever looks at it, an untested edge case Invalidation has carried unremarked since v2. Commit Invalidation's own acceptance criteria explicitly required the opposite: a Memory eligible for Pruning in the same pass must still be evaluated by Commit Invalidation *before* removal, on a real (non-`dryRun`) run — satisfiable only if Commit Invalidation's check runs before Pruning's deletion loop, not after. It therefore sits right after Promotion Audit and before Pruning, mirroring Promotion Audit's own precedent (which runs before Pruning for the same reason: so it sees a contributor's evidence before Pruning can delete it and, with it, that evidence) rather than existing Invalidation's own post-Pruning position. The two mechanisms still never compete — their candidate pools are exact complements of each other — so this ordering choice has no effect on which Memory either one stales, only on whether a Memory that's *also* prune-eligible this same pass gets one more look first.
