# v14 replaces recall's O(n) corpus scan and O(n²) adjacency build with a versioned, on-disk cache, kept outside Shared Memory's git worktree

[Back to CONTEXT.md](../../CONTEXT.md) • [Back to 0025-v19-opportunistic-consolidation-debounce.md](0025-v19-opportunistic-consolidation-debounce.md) • [Back to docs/adr/README.md](README.md) • [Back to hld.md](../architecture/hld.md) • [Back to NEXT_STEPS.md](../../NEXT_STEPS.md)

The 2026-09-16 benchmark refresh (`benchmarks/results/2026-09-15-extended-results.md`) found rAIminiscence's per-turn recall latency scales worse-than-linearly with store size: 178.5ms → 2241.0ms (shim-subprocess median) from 10 to 1500 memories, versus hippo-memory's structurally-bounded per-turn query staying flat at 118–125ms across the same range. At the top of that range, individual reps (up to 2107.2ms) already approach `prompt-recall.ts`'s own internal 2000ms fail-open timeout — this is not just added latency, it risks silently dropping injected context for a turn.

The root cause, traced directly in the code: `recall()` does a full directory read + parse of every memory file on every call (`storage.ts`'s `readAllMemories`), and builds Spreading Activation's `floorAdjacency` with an O(n²) nested loop over the entire scanned pool (`recall.ts:264-276`) — even though the co-access edge map it needs (`coAccessIndex`) is already fully loaded in memory one line earlier. Neither cost is inherent to what a recall needs to compute.

Critically, the exact path the benchmark measured — v10's `UserPromptSubmit` hook — runs this cold, every single turn: `shim.ts` is spawned as a brand-new OS process by the host tool per hook event and calls `recall()` directly; it never reaches the long-lived MCP server (`server.ts`). Any fix confined to that server's process lifetime would not touch the path that actually regressed.

## Decision

1. Fix the two O(n²) hot spots first, independent of caching — both replaced by one O(edges) pass over `coAccessIndex`'s own keys (each already an unordered `id|id` pair) instead of scanning a whole pool per candidate, identical output either way:
   - Spreading Activation's `floorAdjacency` (`recall.ts`), previously an O(n²) nested loop over the full candidate pool.
   - The qualifying set's "direct boost" term (previously `edgeWeightsTo`, now removed), previously an O(n²) loop re-scanning the *entire qualifying set* for *every* qualifying candidate — found only because the first benchmark re-run after the adjacency fix and the cache still showed 1500-memory latency around 1s rather than near-flat; a second instrumented pass traced the remaining cost to this second, independent O(n²) spot the initial fix had missed.
2. Introduce one versioned, on-disk cache per storage root, holding the parsed corpus and the reconstituted embedding/co-access/conflict indices — the four things `recall()` currently rebuilds from scratch on every call. Both the per-turn hook's fresh subprocess and the long-lived MCP server read it the same way: read a small version marker first; if it matches what's currently held, trust the cache; otherwise rebuild from the underlying files and rewrite it.
3. Every writer updates the cache (and bumps the version marker) as part of its own write: `remember` after its single mutation; `consolidate` once at the end of its whole pass rather than per individual promotion/prune/invalidation, so one opportunistic-consolidation run can't turn into dozens of full cache rewrites; a Shared Memory pull, since it changes the same underlying data from outside the current process.
4. The cache lives at `.raiminiscence/cache/`, a sibling to `.raiminiscence/memory/` rather than inside it, because Shared Memory (v11, ADR-0017) makes `.raiminiscence/memory/` itself a git worktree that `flushSharedMemory` runs `git add -A`/`commit`/`push` inside. A cache file inside that directory would risk being swept into the shared history as a purely local, per-machine artifact.

Four sub-decisions, each a genuine alternative that was considered and rejected:

1. **Keep scoring every memory (full-corpus semantics), rather than bound the candidate set the way hippo-memory does (recent/pinned-only).** hippo-memory's structural bound is exactly why its latency stays flat regardless of store size, and was the most direct fix available. Rejected because full-corpus relevance search — not a recency/pin heuristic — is a deliberate differentiator of this project, not an accident; trading it away to match a competitor's latency profile would fix the symptom by discarding the thing rAIminiscence is for.
2. **An on-disk cache, not an in-process one confined to the long-lived MCP server.** An in-process cache only helps calls that reach that server (explicit `remember`/`recall`/`consolidate` tool calls) — it does nothing for the benchmarked regression, which lives entirely in a fresh subprocess spawned per turn. It's also insufficient under Shared Memory, where a sibling process's write is invisible to a cache that only invalidates on this process's own writes. A single on-disk, version-checked artifact is correct for both the fresh-subprocess and persistent-server cases, and for concurrent multi-writer Shared Memory stores.
3. **Not routing the per-turn hook through the persistent MCP server via local IPC.** This would also let the hook reuse a live, warm in-memory cache, but introduces a new local-IPC surface, a server-liveness question (is a server even running for this project right now?), and a fallback path for when it isn't — meaningfully more moving parts than an on-disk cache for the same result. Left as a possible later enhancement if the on-disk cache's ceiling isn't good enough.
4. **A version marker file, over comparing directory/cache mtimes or hashing a directory listing.** mtimes are unreliable across filesystems and git operations (a `git pull` can leave mtimes that don't reflect logical change order); hashing a listing costs more than the read it's meant to avoid. A small counter/timestamp file, read once per call, is the cheapest correct check.

No change to ADR-0001 (flat-file storage, no embedded/vector database): the cache is a derived, rebuildable artifact, not a new source of truth, and is never synced via Shared Memory.

Implementation (the cache module, the `recall.ts` adjacency fix, and an extended-benchmark re-run measuring both per-turn recall latency and opportunistic-consolidation contention) follows in this same pass.
