# v10 Per-Turn Auto-Recall reaches Claude Code and Codex CLI only — Cursor is structurally excluded

v1's `SessionStart` auto-priming (ADR-0005) calls `overview()` once, at session start, and never again — a session that drifts onto a new topic gets no further ambient context unless an agent explicitly calls `recall`. Per-turn auto-recall closes that gap: on every user prompt, the hooks shim calls `recall()` with the prompt's literal text as the query, the same underlying mechanism an explicit `recall` MCP call uses, including its Spaced Repetition and Co-access Edge side effects — it is Recall, automatically triggered, not a new mechanism with its own vocabulary. It deliberately does *not* trigger Consolidation's opportunistic inline check the way `remember`/`recall` normally can; running Clustering/Promotion/Promotion Audit/Pruning/Invalidation/Commit Invalidation on every single prompt has real latency cost and nothing about per-turn timing makes Consolidation more due. It reuses `primer.ts`'s internal timeout (2000ms) rather than whatever budget the host hook itself allows (Claude Code defaults `UserPromptSubmit` to 30s, Codex CLI to 600s) — a hook firing every turn needs to fail open faster than one firing once per session, not slower, so the host's larger allowance is irrelevant to how long this shim should ever wait. Injected content reuses the primer's plain `[kind, confidence] summary` line format, dropping `surfacedVia`/`conflictsWith`/`conflictCandidateWith` — those fields serve an agent actively deciding what to do with a `recall` result; ambient per-turn priming isn't the place to surface conflict-resolution work nobody asked for.

The one shared `raiminiscence-hooks-shim` binary (ADR-0005) now branches on the hook input's `hook_event_name`: `SessionStart` still dispatches to `primer.ts`; `UserPromptSubmit` dispatches to a new sibling module. Neither gets a config toggle — matching `SessionStart`'s own precedent, the only "off switch" for either is not registering the hook at all, consistent with this project's standing bias against config surfaces without demonstrated need (Clustering, Promotion Audit, and Commit Invalidation all shipped the same way: unconditional, no flag).

Unlike `SessionStart`, where ADR-0005 found the identical mechanism reachable on all three clients with only the hook-registration format differing, Cursor has no per-turn hook capable of injecting context back into a turn at all. Its only per-turn hook, `beforeSubmitPrompt`, receives the prompt text but can only allow or block the submission (`continue: true|false` plus a `user_message` shown when blocked) — it cannot add context. Its only context-injecting hook is `sessionStart`, already carrying the existing once-per-session primer. There is no degraded middle ground to offer Cursor; the choice was between shipping the real mechanism to Claude Code and Codex CLI only, or not shipping it anywhere until Cursor's hooks API changes. We chose the former — Cursor users keep exactly today's `SessionStart`-only priming, unchanged, and gain nothing from v10 until Cursor exposes a hook that can inject context per turn.

This is the first ADR in this lineage where the three supported clients diverge in actual capability rather than in hook-registration syntax alone — a future "does this reach all three clients" check can no longer assume ADR-0005's framing (identical behaviour, differing wiring) by default. `raiminiscence-hooks`'s per-client template directories reflect the asymmetry directly: only `templates/claude-code/` and `templates/codex/` gain a `UserPromptSubmit` entry; `templates/cursor/hooks-snippet.json` is untouched by v10.
