# v19 debounces Opportunistic Consolidation and makes Shared Memory's push non-blocking, with `SessionEnd` forcing a full awaited pass

[Back to CONTEXT.md](../../CONTEXT.md) • [Back to docs/adr/README.md](README.md) • [Back to flows.md](../architecture/flows.md) • [Back to hld.md](../architecture/hld.md) • [Back to lld.md](../architecture/lld.md) • [Back to how-it-works.md](../how-it-works.md) • [Back to GOVERNANCE.md](../../GOVERNANCE.md) • [Back to packages/raiminiscence-hooks/README.md](../../packages/raiminiscence-hooks/README.md)

Once a project's Memory store grows large, `remember` and `recall` both schedule a full Consolidation pass on every single call via Opportunistic Consolidation (`triggerOpportunisticConsolidation`) — but that pass runs on the same single-threaded MCP server process handling the next tool call. At 1500 Memories, a `recall` that would normally return in about 30ms instead takes about 950ms whenever it lands behind a pending pass, with no warning and no way to avoid it. Separately, when [Shared Memory](0017-v11-shared-memory-via-git-worktree.md) is enabled, that same pass ends by pushing to a git remote synchronously (`execFileSync`) — a slow or unreachable remote can block the entire MCP server indefinitely, not just for under a second. And because nothing before this pass guaranteed a background pass ever actually got to run before a session ended, a project could go a long time with Pruning, Promotion, Promotion Audit, Commit Invalidation, and Invalidation all silently falling behind, even though every `remember`/`recall` call kept *attempting* to trigger a pass.

## Decision

**Debounce Opportunistic Consolidation, don't move it off-thread.** A new persisted, per-storage-root state (`opportunistic-consolidation-state.ts`, living under `.raiminiscence/cache/` alongside the existing recall cache — see [ADR-0021](0021-v14-versioned-disk-cache-for-recall-latency.md)) tracks the last real pass's timestamp and the call count since. `triggerOpportunisticConsolidation` now fires only when a fixed 15-minute interval or a fixed 20-call count has elapsed since the last real pass, whichever comes first — mirroring [Checkpoint](0020-v13-checkpoint-via-stop-hook.md)'s own 15-minute/20-turn debounce precedent at the same order of magnitude. A storage root with no real pass on record yet is always due, so a fresh store still gets its first opportunistic pass immediately rather than waiting out a full debounce window. Resetting this state is a side effect of `consolidate()` completing any real (non-`dryRun`) pass, regardless of what triggered it — the opportunistic trigger, an explicit `consolidate` tool call, and the new `SessionEnd` forced pass all keep one honest clock with no per-call-site duplication. No new config surface: unlike Spreading Activation's `maxHops` ([ADR-0009](0009-v4-spreading-activation-multi-hop.md)), there's no documented per-project reason to want this tunable.

This state is local-only and never synced via Shared Memory, and is store-level rather than session-level — the first mechanism in this project to need that shape. Every prior debounced mechanism (Checkpoint) used session-scoped hook state (`hook-state-store.ts`) instead, because a nudge is inherently about one session's own turn count. Opportunistic Consolidation's debounce is a property of a storage root's write/read traffic across every session and every process that touches it, so a session-scoped file would reset on every new session for no reason and wouldn't coordinate multiple concurrent Shared Memory writers on the same machine correctly either. Under Shared Memory with multiple concurrent writers, each writer's clock is deliberately independent — reconciling it across writers would require exactly the kind of cross-process coordination this fix is trying to avoid paying for on every call.

**Make the Shared Memory push non-blocking, not the whole pass.** `flushSharedMemory` gains an `awaitPush` option, default `false`. `add`/`commit` stay exactly as synchronous as before (`execFileSync`); only `push` moves to an async git invocation (`runGitAsync`, `execFile`-based) so it no longer blocks the Node.js event loop. When `awaitPush` is off — every caller except one — the push is fire-and-forget, and a failed or unreachable push is swallowed identically to before. `consolidate()`'s `ConsolidateParams` gains the same option, threaded straight through to its internal `flushSharedMemory` call.

**`SessionEnd` forces a full, awaited pass — and now runs for every project, not just Shared Memory ones.** The hooks package's `SessionEnd` step no longer gates on Shared Memory being enabled at all: it always calls `consolidate({ ..., awaitPush: true })`, bypassing the debounce entirely (same as an explicit `consolidate` tool call) and resetting its clock as a side effect. The Shared Memory flush `consolidate()` runs internally stays a no-op when that feature isn't on, exactly as before, so local-only projects now also get a final Pruning/Promotion/Invalidation pass at session end — a benefit that previously only existed for Shared Memory projects, and only as a flush with no local Consolidation at all. Because Opportunistic Consolidation can still have a background pass in flight (via `setImmediate`) when `SessionEnd` fires in the same process, the hook awaits two things first, in order: `settleOpportunisticConsolidation()`, for that pass's own local work (it always runs with `awaitPush: false`, so its own push is still only just kicked off when this settles); then `settlePendingSharedMemoryPush()`, for that just-kicked-off push itself to actually finish. Awaiting only the first would still let `SessionEnd`'s own `add`/`commit` race a push still in flight from the pass it just waited on — the second settle closes that gap, so the forced pass can never race an in-flight one for a second, concurrent `git` invocation against the same worktree. Any failure anywhere in this path — including a failed or unreachable git push — is swallowed, matching every other hook's fail-open contract. Client scope stays exactly as today: Claude Code only (`SESSION_END_HOOK_CLIENTS`); Cursor and Codex CLI have no `SessionEnd`-equivalent hook registered in this project, and extending that registration is explicitly out of scope for this pass — a Cursor/Codex CLI user should not assume this guarantee applies to them.

## Rejected alternatives

1. **Worker threads (or otherwise moving `consolidate()` off the main event loop).** Would fix the contention at its root rather than just reducing how often it's paid, but introduces real new complexity in a single-process Node.js MCP server: message-passing the whole storage-root state across the boundary, or accepting a worker with its own filesystem race window against the main thread's own writes. Rejected for this pass because the debounce alone removes the vast majority of the contention (a pass now runs at most once per 15 minutes or 20 calls, not on every single call) at a fraction of the implementation risk. Revisit if a future re-benchmark, run with the debounce active, still shows per-turn latency contention above target — i.e., debounce alone isn't suffient once call volume or store size grows further.
2. **An incremental, batched, or watermarked redesign of `consolidate()` itself** (processing only Memories touched since the last pass, rather than a full corpus pass each time). Would shrink the cost of each individual pass rather than reducing how often a full pass runs, and is a meaningfully larger redesign touching every Consolidation step's own candidate-selection logic (Clustering, Pruning, Invalidation, Promotion Audit, Commit Invalidation all currently scan the full active corpus). Rejected for this pass for the same reason as worker threads: the debounce is a much smaller, lower-risk change that addresses the measured problem (contention from *frequency*, not from *pass cost* at a given store size — the O(n²) fixes in ADR-0021 already addressed pass cost). Revisit under the same condition as worker threads, and independently if a future benchmark shows a single pass's own wall-clock cost (not just how often it runs) has become the dominant contributor to latency at realistic store sizes.

**Escalation criterion, concretely:** if a future benchmark re-run (mirroring the extended-results methodology from [ADR-0021](0021-v14-versioned-disk-cache-for-recall-latency.md)) shows shim-subprocess or MCP-server per-turn latency contention still above target with the debounce active — i.e., a `recall`/`remember` call still measurably stalls behind a Consolidation pass at realistic store sizes and call volumes — that is the trigger to revisit worker threads and/or an incremental redesign, not a re-argument from first principles.

No change to [ADR-0001](0001-flat-file-markdown-storage.md) or [ADR-0021](0021-v14-versioned-disk-cache-for-recall-latency.md): the new debounce state is a derived, rebuildable artifact exactly like the existing recall cache, never a source of truth and never synced via Shared Memory.

Implementation (the debounce state module, `flushSharedMemory`'s `awaitPush`, the `SessionEnd` hook rewrite, and the accompanying tests) follows in this same pass.
