# v11 Shared Memory propagates over git (orphan-branch worktree, per-record index files, recency-based merge driver) — no new transport, no live sync daemon

Team/agent-shared memory is delivered entirely over git rather than a new live sync mechanism: `.raiminiscence/memory/` becomes a `git worktree` checkout of a dedicated orphan branch, never merged into the project's own code branches, created automatically the first time a project's `.raiminiscence.config.json` sets `sharedMemory: true`. This keeps ADR-0003's stdio-only MCP transport completely untouched — sharing needs no socket, no server process, no auth story; git is already a hard dependency of every project this tool runs in, so this is the more literal "zero infrastructure" answer once multi-writer sharing is in scope at all. A live sync protocol was considered and rejected for adding exactly the transport/infrastructure surface ADR-0003 explicitly ruled out.

The three packed indices (`embeddings.json`, `co-access.json`, `conflict.json`) are split into one file per record, mirroring the one-file-per-Memory pattern ADR-0001 already established for exactly this reason. This means two simultaneous writers — whether two clones on different machines merging later, or two agent processes on the same machine writing at the same instant — never collide on *different* records, and the format becomes naturally git-mergeable (new/deleted files merge cleanly on their own). A real race remains only when two writers touch the exact same record at the same instant: co-access weight increments are left unprotected (a lost `+2` bump is invisible and self-corrects on the next co-occurrence), while Conflict Verdicts get an optimistic read-check-write-with-retry, since silently dropping an agent's explicit judgment call is a real correctness problem a cheap weight bump isn't.

A genuine git-level merge conflict on a shared record (e.g. two clones independently stale vs. retract the same Memory before either pulled) is resolved automatically by a custom git merge driver favoring whichever side carries the more recent `updatedAt` field, newly added to all three record types for exactly this purpose — applied uniformly, with no special-cased precedence between transition types (no hardcoded "retracted beats stale" rule). Commits are batched (at Consolidation completion and session end, not per-write) and auto-pushed, but a pull only ever happens explicitly, via a new `SessionStart`-hook step that surfaces something to the agent only when an actual merge/conflict occurred — never a silent background merge. This is deliberately not exposed as a new MCP tool, preserving the project's existing seven-tool discipline.

This is unrelated to Conflict/Conflict Candidate, which flag two Memories whose content semantically disagrees. A Shared Memory merge conflict is a write-time race between two updates to the same record; the existing Conflict Candidate flow (cosine similarity ≥0.82, surfaced on the next Recall) is reused as-is, unchanged, to catch two independently-written near-duplicate Memories that a merge brings together — no new detection mechanism was built for that case.
