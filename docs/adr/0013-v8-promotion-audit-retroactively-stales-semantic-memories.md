# v8 Promotion Audit retroactively stales Semantic Memories whose contributors turned bad

[Back to CONTEXT.md](../../CONTEXT.md) • [Back to docs/adr/README.md](README.md) • [Back to hld.md](../architecture/hld.md) • [Back to lld.md](../architecture/lld.md)

ADR-0011 and ADR-0012 each named the same gap and left it open: a Semantic Memory promoted *before* a confirmed `"contradicts"` Conflict Edge existed between its contributors, or *before* a contributor's feedback turned net-negative, is "left completely untouched, with no retroactive scan of its `promotedFrom` ids." Both v6's and v7's gates are prevention-only, checked at the moment Clustering's seed/candidate loop runs; neither ever revisits a Promotion already made. Meanwhile the evidence `promotedFrom` traversal would need can itself disappear: Pruning physically deletes a Memory and, with it, that Memory's Conflict Edges (`removeConflictEdgesForId`), while a contributor that survives Promotion keeps accumulating feedback indefinitely (`consolidationSurvivalCount` bumps it, nothing else changes its eligibility to keep being recalled and rated).

We chose a new step, Promotion Audit, that re-checks every already-promoted Semantic Memory's `promotedFrom` contributors against current Conflict Edge and Outcome Feedback state, and sets a caught Semantic Memory's Confidence Tier to `stale` — the same transition Invalidation performs, but Promotion Audit is deliberately its own term rather than a second trigger folded into Invalidation, which stays anchored specifically to Related Files/git evidence. It runs automatically inside every `consolidate` call, with no separate tool and no config surface, matching the automatic/evidence-driven shape of Invalidation rather than the deliberate-request shape of Forget/Supersession: both a Conflict Edge verdict and a feedback tally are already-recorded facts by the time the audit runs, not new judgment calls it makes itself. It runs before Pruning in the same pass, so it sees Conflict Edges and feedback counts before anything in that same pass is swept away — a contributor already pruned in an *earlier* pass is simply invisible to the check, which is accepted as an inherent, best-effort limitation rather than something worth a retention policy of its own. The Conflict-Edge check looks at *all pairs* within `promotedFrom`, not seed-to-candidate only like live Clustering: `promotedFrom` is a flat `string[]` with no seed identity preserved past promotion, so an all-pairs check avoids inventing an ordering contract nothing else in the codebase relies on, and as a side effect closes ADR-0011's own named non-seed blind spot for everything already promoted. The feedback check reuses `isNetNegativeFeedback` per contributor unchanged from v7. The audit is stateless — every Semantic Memory is re-examined on every `consolidate` call, with no watermark field and no `schemaVersion` bump, holding the same "no new frontmatter field" line every version since v2 has held. `consolidate`'s result gains two counts, one per triggering signal, never combined into one number, matching the project's standing discipline (see ADR-0012) against conflating what two distinct mechanisms count.

This is a fourth entry in the ADR-0010/0011/0012 lineage, and the first that looks backward instead of forward: 0010, 0011, and 0012 each gate a mechanism at the moment it would otherwise let something through; Promotion Audit instead re-examines decisions Clustering and Promotion already made, using signals that didn't exist yet, or hadn't yet turned, at the time. It touches no other mechanism directly — Recall and Overview already exclude `stale` Memories on their own, live Clustering's seed-to-candidate shape is untouched, and a staled Semantic Memory has no reversal path, the same immutability principle Invalidation and Forget both already follow.
