# v7 Negative Feedback keeps a Memory out of Clustering entirely

[Back to CONTEXT.md](../../CONTEXT.md) • [Back to docs/adr/README.md](README.md) • [Back to hld.md](../architecture/hld.md) • [Back to lld.md](../architecture/lld.md)

Clustering (unchanged since v1, extended in v6 to gate on Conflict Edges) decides candidacy on embedding similarity and, since v6, on a confirmed `"contradicts"` verdict against the seed — it has no awareness of whether a Memory has ever actually proven useful. Outcome Feedback (v2) already tracks exactly that, per Memory, via `positiveFeedbackCount`/`negativeFeedbackCount`, but the only consumer of those counts is `computeStrength`'s decay arithmetic. Left unmodified, a Memory with a documented history of being unhelpful can still seed or join a Cluster on similarity alone and get folded into a new, permanent Semantic Memory — the exact content that already proved unhelpful, now generalized into a claim Recall will surface as `inferred` fact going forward.

We chose to exclude a net-negative Memory (`negativeFeedbackCount > positiveFeedbackCount`) from the episodic candidate pool entirely, before Clustering's seed/candidate loop ever runs, rather than add a relational check like v6's. v6's gate makes sense as a pairwise comparison because a `"contradicts"` verdict is a fact about *two* Memories; a Memory's own feedback history is a fact about *itself* alone, so checking it only when the Memory happens to be offered as a candidate (leaving it free to seed a Cluster instead) would miss the exact case this feature exists to prevent. Net-negative, not any single negative count, is the trigger — one unhelpful recall among many helpful ones is Outcome Feedback's decay signal to absorb, not grounds to block Consolidation outright, and a history of being unhelpful is the pattern v6's own scoping notes named as the eventual candidate for this version. Like v6's gate, this one is unconditional (no config surface) and prevention-only — a Semantic Memory a prior Consolidation run already promoted from a Memory that only turned net-negative afterward is left untouched, with no retroactive scan of `promotedFrom` ids.

This is a third gate in the ADR-0010/0011 lineage — all three keep Consolidation-adjacent machinery from compounding a signal that shouldn't be compounded — but it's architecturally distinct from both: ADR-0010 and ADR-0011 each gate a *relationship* (a Conflict Edge between two specific Memories) at their own point of consumption, while this gate filters on a *property of one Memory* before any relationship is even considered, so it lives beside Clustering's existing `isActive`/`!promoted` pool filters rather than inside its seed/candidate loop. It doesn't touch Co-access Edge, Spreading Activation, or the v6 Conflict Edge gate, and none of those touch it. `consolidate`'s result reports this separately from `blockedJoinAttempts` (`feedbackExcludedCount` — the count of distinct Memories filtered, not per-attempt) precisely because the two mechanisms count different things: `blockedJoinAttempts` counts relational rejections during the seed/candidate loop, this counts Memories that never reached that loop at all.
