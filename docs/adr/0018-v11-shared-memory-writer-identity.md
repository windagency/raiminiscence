# v11 Shared Memory adds a writer-identity field to Memories and Conflict Verdicts only

[Back to CONTEXT.md](../../CONTEXT.md) • [Back to 0016-team-shared-memory-becomes-a-future-direction-adr-0003-flagged.md](0016-team-shared-memory-becomes-a-future-direction-adr-0003-flagged.md) • [Back to 0020-v13-checkpoint-via-stop-hook.md](0020-v13-checkpoint-via-stop-hook.md) • [Back to docs/adr/README.md](README.md) • [Back to hld.md](../architecture/hld.md) • [Back to lld.md](../architecture/lld.md) • [Back to user-guide.md](../user-guide.md)

Once one memory store has multiple writers (ADR-0017), Source's existing `{client, model}` provenance no longer says *who* — Source records which tool wrote a Memory, not which person or which running instance. Shared Memory adds two more fields, for traceability: the local git identity (`user.name`/`user.email`, already required for ADR-0017's git-based propagation, so no new setup cost) and a fresh id generated once per MCP server subprocess lifetime (this project's stdio transport already spawns one process per client session, so this needs no new concept of "session").

These fields are added as a new `writer: { gitName?: string; gitEmail?: string; sessionId: string }` object — a sibling to a Memory's existing `source` field, not merged into it, since a Conflict Verdict has no `source` field to merge into either and both record types need `writer` identically. Applied to Memory frontmatter and to a Conflict Verdict record only. Co-access edges and embeddings deliberately do not get them — nobody asserts a co-occurrence or a vector the way a Memory's content or a Conflict Verdict's judgment call is asserted, and adding an unused identity field to a purely mechanical, derived signal would be exactly the kind of premature schema growth this project avoids elsewhere.
